# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 우선순위

**프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 그것이 우선한다.** 이 파일은 기본값(fallback)이며, 프로젝트 규칙이 다루지 않는 부분에만 적용된다.

## 1. 적용 기준

### TDD 필수

- **비즈니스 로직**
- **API** (핸들러, 요청/응답 처리, 에러 매핑)
- **유틸 / 순수 함수**
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성한다)

### TDD 불필요

- **타입 정의** (`type`, `interface`)
- **설정 파일** (tsconfig, eslint, vite 설정 등)
- **순수 UI** (로직 없는 마크업/스타일)
- **SQL** (스키마, 마이그레이션)

경계가 모호하면 **로직이 한 줄이라도 있으면 TDD 대상**으로 본다.

## 2. RED - GREEN - REFACTOR

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 담지 않는다.
- **반드시 실행해서 실패를 눈으로 확인한다.** 실행하지 않은 RED는 RED가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 오타, import 오류, 문법 오류, 잘못된 셋업으로 인한 실패는 RED가 아니므로 테스트를 고쳐 다시 실행한다.

### GREEN: 최소 구현

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** - 아직 테스트가 요구하지 않는 기능, 분기, 옵션은 넣지 않는다.
- **신규 테스트와 기존 테스트가 모두 통과**하는지 전체 테스트를 실행해 확인한다.

### REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **테스트는 계속 green이어야 한다.** 변경마다 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED에서 한다.

### 반복

REFACTOR가 끝나면 **다음 동작에 대한 RED로 돌아간다.** 요구사항의 모든 동작이 테스트로 덮일 때까지 반복한다.

## 3. 삭제 강제 규칙

**테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작한다.**

- "참고용"으로 남겨두기 금지. 주석 처리, 다른 파일로 옮겨두기, 머릿속에 두고 베끼기 모두 포함한다.
- 삭제한 코드를 테스트에 맞춰 "복원"하지 않는다. 테스트가 요구하는 만큼만 새로 쓴다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| 너무 단순해서 테스트 불필요 | 단순한 코드가 가장 쉽게 깨지고, 테스트도 가장 빨리 쓴다. 30초면 된다. |
| 나중에 테스트를 추가하겠다 | 나중은 오지 않는다. 사후 테스트는 구현에 맞춰 쓰이므로 버그를 못 잡는다. |
| 시간이 없다 | 테스트 없는 코드는 디버깅과 재작업으로 더 많은 시간을 쓴다. 급할수록 지킨다. |
| 이미 쓴 코드를 삭제하면 낭비다 | 매몰비용이다. 검증되지 않은 코드를 유지하는 비용이 더 크고, 다시 쓰는 건 빠르다. |
| 프로토타입이다 | 프로토타입은 그대로 프로덕션이 된다. 버릴 코드라면 버리고, 남길 코드라면 TDD로 쓴다. |

## 체크리스트

- [ ] 최소 코드로 신규+기존 테스트가 모두 통과하는가?
- [ ] 리팩터링 중 green을 유지했고 새 동작을 넣지 않았는가?
- [ ] 테스트보다 먼저 쓴 프로덕션 코드가 남아있지 않은가?
