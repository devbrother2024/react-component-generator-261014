# Commit

변경사항을 읽고, 의미 단위로 나누고, 컨벤션에 맞는 한국어 메시지를 만들어 **승인 절차 없이 바로** 커밋한다.
사용자가 커밋을 요청한 시점에 이미 의도를 밝힌 것이므로 다시 묻지 않는다. 대신 커밋 후 결과를 투명하게 보고하고, 로컬 커밋은 `git reset --soft HEAD~N`으로 되돌릴 수 있음을 안내한다.

## 절차

### 1. 변경사항 분석
다음을 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 기존 메시지 스타일 참고
```

- 변경이 전혀 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.
- 이미 staged 된 항목이 있으면 사용자가 의도해서 올린 것일 수 있으니 존중한다.
- untracked 파일은 내용을 열어 확인한다. `.env`, 키/토큰, 대용량 바이너리, 빌드 산출물(`node_modules`, `dist` 등)처럼 커밋하면 안 될 것이 보이면 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류
하나의 커밋은 "한 가지 이유로 생긴 변경"이어야 나중에 리뷰·revert 하기 쉽다. 파일 단위가 아니라 **목적 단위**로 묶는다.

- 기능 추가, 버그 수정, 리팩터링, 설정/문서 변경이 섞여 있으면 분리한다.
- 같은 파일 안에서 목적이 다른 hunk가 섞였다면 `git add -p`로 나눌 수 있는지 검토한다. 어렵다면 하나로 묶고 그 사실을 사용자에게 알린다.
- 변경이 작고 목적이 하나면 커밋 1개로 충분하다. 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성 (한국어)

형식:

```
<type>: <요약>

<본문 - 선택>
```

| type | 용도 |
|------|------|
| feat | 새 기능 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 빌드·설정·의존성·기타 잡무 |

보조적으로 `docs`, `style`, `test`가 더 정확한 경우(문서만, 포맷만, 테스트만 변경)에는 그것을 써도 된다.

작성 원칙:
- 요약은 한 줄, 50자 안팎, 마침표 없이. "무엇을 했는가"를 명사형/동사형으로 간결하게 쓴다. (예: `feat: 컴포넌트 생성 폼에 props 입력 추가`)
- diff에서 실제로 확인된 내용만 쓴다. 추측으로 의도를 지어내지 않는다.
- 요약만으로 "왜"가 전달되지 않을 때만 본문을 붙인다. 본문은 변경 이유와 맥락 위주로 쓴다.
- `git log`에서 이미 쓰이는 스타일(scope 사용 여부 등)이 있으면 따른다.

### 4. 커밋 실행

승인을 기다리지 않고 커밋 단위마다 해당 파일만 add 하고 커밋한다.

```bash
git add <파일들>          # git add -A / . 는 의도치 않은 파일이 섞이므로 피한다
git commit -m "<type>: <요약>" 
```

본문이 있으면 `-m`을 한 번 더 쓰거나 heredoc을 사용한다. 이 세션/환경의 시스템 지침이 커밋 메시지 끝에 붙이라고 지정한 attribution 줄이 있으면 본문 끝에 포함한다.

### 5. 결과 보고

`git log --oneline -N`으로 만든 커밋을 보여주고, 각 커밋에 포함된 파일과 제외한 파일(이유 포함)을 간단히 알린다. 사용자가 메시지나 분류를 바꾸고 싶어 하면 그때 `git reset --soft`로 되돌려 다시 커밋한다.

## 하지 말 것
- push는 하지 않는다. 사용자가 따로 요청할 때만 한다.
- `--no-verify`, `--amend`, force 옵션은 사용자가 요청하지 않으면 쓰지 않는다. pre-commit hook이 실패하면 원인을 보고하고 고친 뒤 새 커밋으로 만든다.
- 커밋을 위해 사용자의 변경사항을 `reset`/`checkout`/`stash`로 건드리지 않는다.
